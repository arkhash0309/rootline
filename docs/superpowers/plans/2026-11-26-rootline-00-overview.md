# Rootline Implementation Plan — 00 Overview and Shared Contracts

> **For agentic workers:** Execution follows the swarm protocol in §7 of this file: a Haiku 5.5 coordinator dispatches Sonnet 5.5 implementers (high effort), Opus 5.5 reviewers (high effort) and an Opus 5.5 planner (high effort) per `CLAUDE.md` → "Agent models and roles", using the stage order in `2026-11-26-rootline-schedule.yaml`. Within each task, use superpowers:subagent-driven-development's per-task discipline (implement → spec-compliance review → code-quality review). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build Rootline exactly as specified in `docs/superpowers/specs/2026-11-25-rootline-design.md` (SPEC-ROOTLINE-001 v2.0, approved by the owner on 2026-11-26), in eight weekly waves.

**Architecture:** A trimmed OpenTelemetry Demo shop runs in a k3d (local) or GKE (cloud) cluster next to the Rootline platform. The Fault Lab injects labelled faults and captures replayable snapshots. A LangGraph planner/executor agent investigates through three OAuth-protected MCP servers. A policy gate (OPA) decides whether its GitOps fix merges automatically, needs a passkey-backed approval, or is denied. An offline eval runner replays snapshots to produce the benchmark.

**Tech Stack:** Python 3.12 (uv workspace, FastAPI, SQLAlchemy 2.0, Alembic, Pydantic 2, LangGraph 1.x, official `mcp` and `anthropic` SDKs, DuckDB, Drain3, ruptures, fastembed), Next.js 16 / React 19 / TypeScript 5 / Tailwind 4, Postgres 16 + pgvector (CloudNativePG), Keycloak 26.8, OPA 1.x, Kyverno, ArgoCD 3.x, Helm, Terraform 1.x (google provider 7.x), k3d, GKE, GitHub Actions, Langfuse Cloud, go-task.

## Global Constraints

Every task in every wave file implicitly includes these. Values are copied from the spec; the spec wins if this list and the spec ever disagree.

- **Spec is the source of truth.** Cite requirement IDs in every task, test docstring and PR (spec §0.2). If the spec is silent, follow spec §0.3: simplest → cheapest → safest; record an ADR with label `spec-gap` and a row in spec §26, in the same PR.
- **Documentation rule:** every document you write follows `CLAUDE.md` → "Documentation rule" (exact values, no vague words, full interfaces).
- **Repository layout** is exactly GEN-001. New top-level directories require an ADR.
- **Python:** 3.12.x. One uv workspace (GEN-002). Import package names: `rootline_api`, `rootline_agent`, `rootline_gate`, `rootline_faultlab`, `rootline_mcp_k8s`, `rootline_mcp_telemetry`, `rootline_mcp_gitops`, `rootline_common`, `rootline_mcpkit`, `rootline_llm`, `rootline_schemas`, `rootline_eval`.
- **Node:** 24.x LTS. Console in `apps/console`.
- **Versions:** every pinned version is read from `versions.yaml` (GEN-050). Never hard-code a version anywhere else; files that cannot read YAML are generated by `scripts/render_versions.py`.
- **Automation (GEN-041):** Taskfile tasks use only `task` built-ins, `uv run python scripts/<name>.py`, or the GEN-040 tools. No bash, PowerShell or `make` syntax in tasks. No shell scripts outside container images and CI.
- **Commits (GEN-022, PG-20):** Conventional Commits with optional scope = component directory (`feat(agent): …`). Every agent commit ends with the trailer of the role that authored it, exactly as in §7.1 "Commit attribution trailers": implementer `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`; planner `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`; coordinator `Co-Authored-By: Claude Haiku 5.5 <noreply@anthropic.com>`; the reviewer never commits. A commit example in a wave file that shows another trailer is wrong; the §7.1 table decides.
- **Formatting (CI-001, G5, PG-19):** a plan code block fixes a file's content, not its formatting. Before every commit that adds or changes `*.py` files, the implementer runs `uv run ruff format <each added or changed .py file>` and then `uv run ruff check <the same files>`, which must exit 0 (a `ruff check` finding is fixed by hand, never by disabling the rule). The one exception (PG-21, ADR 0040 item 1): a `subprocess` call whose argument list is a parameter, a variable, a list literal with non-literal elements, or a list built in code carries `# noqa: S603 - <justification>` on the line where ruff `0.17.6` reports `S603`, with the justification on that same line, and only where `uv run ruff check` reports `S603`, because an unused `# noqa: S603` fails with `RUF100`. Example: `return subprocess.run(  # noqa: S603 - cmd is an argument list run without a shell (GEN-041)`. `S607` (bare executable name) is never suppressed: such calls go through `scripts.proc.run`. `# noqa: BLE001` is never written, because rule family `BLE` is not selected and the comment fails with `RUF100`; a deliberate broad handler is written `except Exception:` or `except Exception as <name>:`, followed on the same line by `# <justification>`. No other lint suppression (`# noqa`, `per-file-ignores`, `ignore` entries) is allowed without its own ADR. A committed file that differs from its plan block only in what `ruff format` changes (line wrapping, blank lines, quote style, trailing commas, comment spacing) complies with the plan; reviewers do not flag those differences. Markdown files are excluded from ruff (`[tool.ruff] extend-exclude = ["*.md"]`, W1-T16 Step 0), so code blocks in specs, plans and the wiki are never reformatted by tooling.
- **Branches (GEN-020/021):** work on `feat/<slug>`, `fix/<slug>` or `docs/<slug>` from `develop`; squash-merge into `develop`; release PR `develop → main` at each week end titled `release: milestone <N>` (merge commit).
- **PRs (GEN-023):** use `.github/pull_request_template.md` with headings Summary, Requirement IDs, Wiki pages updated, Tests, Screenshots (UI only), Cost impact.
- **Wiki (WIK-020):** every PR touching `services/`, `libs/`, `deploy/`, `infra/`, `policies/` or `eval/` updates the affected `wiki/components/*.md` or runbook, appends to `wiki/log.md`, updates `wiki/status.md` when a plan task changes state, and adds an ADR for any new decision. Run `task wiki:lint` before pushing.
- **TDD (TST-003):** every non-UI module is written test-first. Tests live under `tests/` next to the package. Each test docstring cites requirement IDs, e.g. `"""Verifies SEC-021."""`.
- **Coverage (TST-002):** ≥ 80% lines per Python package; ≥ 70% branches for `rootline_mcpkit.redact`, `rootline_agent.guard`, `rootline_api.auth`, `rootline_gate`; console ≥ 70% lines for `app/(bff)/` and `lib/`.
- **Services (ARC-020):** Python HTTP services listen on 8080 (console 3000), Service port 80, DNS `<component>.rootline.svc.cluster.local`, and expose `/healthz`, `/readyz` (503 with `{"failing":[...]}` when a hard dependency is down) and `/metrics`.
- **IDs and time:** primary keys are ULIDs (26 chars, Crockford base32) stored as `text`. Timestamps are RFC 3339 UTC with `Z`; MCP outputs use millisecond precision (MCP-002).
- **Errors:** HTTP APIs use RFC 9457 problem+json with the codes in API-002. MCP tools use the error envelope and codes in MCP-005.
- **Models (AGT-050):** exactly `claude-haiku-5-5` and `claude-sonnet-5-5`. `claude-opus-5-5` is not used. All LLM access goes through `rootline_llm` (AGT-004); no other module imports `anthropic` or calls Ollama.
- **Budgets:** LLM keys and caps per CST-001 (`dev` 16, `eval` 48, `ci` 5 (per run 0.50), `cluster` 6 USD). Never spend money without the owner's explicit go-ahead for that run; every step that calls a paid API says so in bold.
- **Secrets (SEC-101):** never in Git, Helm values, Terraform variables or state. `.env.local` / `.env.gke` are gitignored; `.env.example` lists every key with empty values.
- **Container security (INF-022):** `runAsNonRoot: true`, `runAsUser: 10001`, `readOnlyRootFilesystem: true`, `allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]`, `seccompProfile: RuntimeDefault`; requests and limits from ARC-030.
- **Outward-facing actions** (creating repositories, GitHub Apps, deploy keys, rulesets, GCP projects, buying credits, Hugging Face publication, pushing to `main`) are performed by the owner or by an agent only after the owner confirms in the session. Each such step is marked **[OWNER]** or **[CONFIRM]**.
- **GitHub account:** always `arkhash0309`. Never use any other account configured in `gh`.
- **WSL (GEN-040, GEN-041, PG-17):** all development — every Claude Code session (coordinator and subagents), `task`, `uv`, Docker, k3d, kind, Ollama, git — runs inside WSL 2 Ubuntu 26.04 LTS, in the repository at `/home/arkhash0309/projects/rootline` on the WSL filesystem. ## 1. How to execute these plans

1. Read this overview completely (including §7), then the wave file for the current week.
2. Load the `rootline-wiki` skill (exists after W1-T05) and follow it before and after every task.
3. Execute each week's stages in the order given by its **Execution schedule** section (identical to `2026-11-26-rootline-schedule.yaml`). A `sequential` stage runs its tasks one after another; a `parallel` stage runs its tasks simultaneously in separate git worktrees and then integrates them through the §7 integration gate. A task's **Depends on** line is always satisfied by the stage order.
4. One task = one branch `feat/<wave>-<task-slug>` (for example `feat/w2-scenario-generator`) = one PR. Sequential tasks open their PR into `develop`. Parallel tasks open their PR into the stage's integration branch `integration/<stage id lowercase>` (for example `integration/w2-p1`), which reaches `develop` as one squash-merged PR (§7.6). Tasks marked **[OWNER]** have no PR unless they change files.
5. A task is done only when: its tests pass, its reviewer verdict is `APPROVE`, the wiki obligations are met, its work is squash-merged into `develop` (directly, or through its integration PR), its deferred steps (§7.3) are complete, and `wiki/status.md` lists it under Done.
6. At the end of each wave, run the wave's **Acceptance** section and open the release PR (MS-002).

## 7. Swarm execution and integration protocol

Decision record: PG-16 (§5) and ADR 0035. Roles and models are fixed by `CLAUDE.md` → "Agent models and roles".

### 7.1 Roles

| Role | Model | Effort | Agent | Does |
|---|---|---|---|---|
| Coordinator | `claude-haiku-5-5` | `medium` | top-level session (`claude --model claude-haiku-5-5`) | runs this protocol; dispatches subagents; runs gates and git operations; talks to the owner |
| Planner | `claude-opus-5-5` | `high` | `rootline-planner` | plan, schedule and spec changes; spec-gap decisions; re-planning; conflict-resolution design |
| Implementer | `claude-sonnet-5-5` | `high` | `rootline-implementer` | one task per dispatch, test-first |
| Reviewer | `claude-opus-5-5` | `high` | `rootline-reviewer` | task reviews and integration reviews |

Every Agent-tool dispatch passes `subagent_type`, `model` (`opus`, `sonnet`) and `effort: "high"` explicitly. Implementers of parallel tasks are dispatched with `isolation: "worktree"`.

#### Commit attribution trailers (GEN-022, PG-20, ADR 0039)

Every commit written by an agent ends with a trailer block: one blank line, then the `Co-Authored-By:` lines below, one per line, with nothing after them. The trailer names the model of the session that wrote the commit message, not the model that planned or reviewed the change. This table decides over every commit example in the wave files and over the GEN-022 parenthetical "currently `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`" in the spec. The trailer bullet of `CLAUDE.md`/`AGENTS.md` "Commit rules (GEN-022)" repeats this table (owner decision 2026-11-26); if the two ever differ, this table decides.

| Role (model) | Commits it writes | Trailer block (exact) |
|---|---|---|
| Implementer (`claude-sonnet-5-5`) | every commit on a task branch (`feat/`, `fix/`, `docs/` task branches), in every mode (`implement`, `fix-review`, `fix-gate`, `resolve-conflict`), on `feat/<task branch slug>-deferred` branches (§7.3), on `fix/<stage>-integration` branches (§7.8), and in the `rootline-env` / `rootline-env-e2e` repositories | `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>` |
| Planner (`claude-opus-5-5`) | spec, plan, schedule and ADR commits on its `docs/<slug>` branches | `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>` |
| Reviewer (`claude-opus-5-5`) | none: the reviewer is read-only and never edits, commits, pushes or merges (`.claude/agents/rootline-reviewer.md`). If a reviewer report says it changed or committed anything, the coordinator discards the review, resets the branch to its pre-review head, and dispatches a fresh review | — (no trailer, because no commits) |
| Coordinator (`claude-haiku-5-5`) | `chore: regenerate lockfile` and `chore: regenerate generated files` (§7.4); the `wiki/status.md` commit `docs(wiki): update status for <stage id>` (§7.6 step 5, §7.9 step 3); revert commits (§7.8); the merge commits into integration branches and the squash commits into `develop` that it creates with `gh pr merge` (commands below) | `Co-Authored-By: Claude Haiku 5.5 <noreply@anthropic.com>` |
| Owner, without an agent | any commit, the release merge `develop → main` (MS-002) | no trailer |

Coordinator commands (bash in WSL, `<n>` = PR number):

| Commit | Command |
|---|---|
| Merge a task PR into `integration/<stage>` (§7.6 step 2) | `gh pr merge <n> --merge --body "Co-Authored-By: Claude Haiku 5.5 <noreply@anthropic.com>"` (GitHub's default merge title `Merge pull request #<n> from arkhash0309/<branch>` is kept; the merged task commits keep their own trailers) |
| Squash a PR into `develop` (§7.6 step 5, sequential task PRs, GEN-021) | the squash block below. The squash commit's subject is `<PR title> (#<n>)`; its body is exactly the trailer block: every distinct `Co-Authored-By:` line of the squashed commits in first-appearance order, then the Haiku line once |
| Revert a squash commit `<sha>` (§7.8), on branch `fix/revert-<PR number>` from `develop`, opened as the PR `revert: <original subject>` | `git revert --no-commit <sha>` then `git commit -m "revert: <original subject>" -m "This reverts commit <sha>." -m "Co-Authored-By: Claude Haiku 5.5 <noreply@anthropic.com>"` |

Squash block (set `n` to the PR number first, for example `n=12`):

```bash
title=$(gh pr view "$n" --json title --jq .title)
trailers=$( { gh pr view "$n" --json commits --jq '.commits[].messageBody' | grep '^Co-Authored-By: '; echo 'Co-Authored-By: Claude Haiku 5.5 <noreply@anthropic.com>'; } | awk '!seen[$0]++' )
gh pr merge "$n" --squash --subject "$title (#$n)" --body "$trailers"
```

Failure behaviour: if `gh pr view` fails (network, authentication), the coordinator does not merge and retries once after 60 s; on a second failure it stops and reports to the owner. A squash that GitHub rejects (required check `ci / required` not green, merge conflict) is not retried with other flags; the coordinator handles it as a gate failure (§7.8). Commits already on `develop` or `main` before 2026-11-26 (for example `4898699`, which carries only the Haiku trailer) are never rewritten.

### 7.2 Schedule and stages

`docs/superpowers/plans/2026-11-26-rootline-schedule.yaml` is the single source of truth for stage order. Schema:

```yaml
version: 1
max_parallel_implementers: 3
weeks:
  - week: 2
    stages:
      - id: W2-P1                 # S = sequential, P = parallel; unique; order = execution order
        mode: parallel            # sequential | parallel
        after: [W2-S1]            # stages that must be complete first
        uses_cluster: false       # parallel stages are always false
        tasks:
          - id: W2-T03
            branch: feat/w2-algorithms
            combined_with: []     # other task IDs implemented on the same branch (W1-T03 + W1-T04)
            owns: [services/mcp-telemetry/**, libs/py-mcpkit/rootline_mcpkit/windows.py]
            excludes: []          # globs carved out of owns
            pre_steps: []         # step numbers the coordinator completes before dispatch
            deferred_steps: []    # step numbers run in the stage named by deferred_to
            deferred_to: null     # stage ID, required when deferred_steps is non-empty
```

Glob syntax of `owns`, `excludes` and `always_allowed` (PG-21, ADR 0040 item 6): paths are relative to the repository root with `/` separators; patterns are gitignore-style (`pathspec.GitIgnoreSpec`, `**` matches across directories, `*` within one path segment), but a pattern without `/` is anchored at the repository root (it is matched as `/` + pattern). So `pyproject.toml` matches only the root `pyproject.toml`; `**/pyproject.toml` matches it at every depth. `scripts/swarm_lib.py` `matches(path, globs)` implements this.

Rules:
1. At most `max_parallel_implementers` = **3** implementer subagents run at once (12 GB WSL VM with 16 CPUs: each worktree runs its own `uv sync`, pytest and testcontainers; memory, not CPU, is the limit). Tasks of a larger parallel stage wait in schedule order for a free slot.
2. Parallel stages never use the local cluster. Before dispatching a parallel stage whose tasks run integration tests, the coordinator runs `task stop` if the cluster is running, and `task start` again afterwards.
3. Two tasks that each add an Alembic revision are never in the same parallel stage (one linear chain, §4).
4. No two tasks in one parallel stage own the same path, except the always-allowed paths in §7.4. `scripts/swarm_schedule.py validate` enforces this.
5. Shared contracts (§3) are changed only by sequential tasks or by the planner. A parallel implementer that needs a contract change reports `BLOCKED`.

### 7.3 Steps that never run inside a parallel worktree

| Step kind | How it is recognised | Who runs it, where |
|---|---|---|
| Owner and confirmation steps | marked **[OWNER]** or **[CONFIRM]** | coordinator with the owner; before dispatch when listed in `pre_steps`, otherwise in `deferred_to` |
| Paid steps | marked **[PAID]** | coordinator, after the owner's go-ahead, in `deferred_to` |
| Cluster steps | uses the local k3d cluster, kind, GKE, `task up`, `task images`, `task stop/start`, `kubectl`, `k3d`, `kind`, `helm install`, `task lab:*`, `task e2e*`, `task gke:*`, `task test:k8s` | an implementer dispatched by the coordinator on the integration result (on `develop` after the integration PR merges), in `deferred_to` |
| Steps needing other tasks of the same stage | named in `deferred_steps` | same as cluster steps |
| Steps that need subagents (for example the writing-skills baseline in W1-T05) | named in `pre_steps` / `deferred_steps` | coordinator, which dispatches a fresh implementer as the test subject |

A task is not done until its deferred steps are done (§1 step 5). Each `deferred_to` stage is a sequential stage of the same week, and its deferred steps run at the start of that stage, before its own tasks, in schedule order.

Commits around deferred steps: the implementer commits all non-deferred work at the end of its last non-deferred step, using the task's commit message, even when the plan's commit step comes after a deferred step. Deferred steps that change files (measurements, wiki records, generated outputs) commit on a branch `feat/<task branch slug>-deferred`, opened as a PR into `develop` and reviewed like a sequential task.

### 7.4 Ownership and always-allowed paths

A parallel task may change only its `owns` globs (minus `excludes`) plus these always-allowed paths:

| Path | Handling at integration |
|---|---|
| `wiki/log.md` | append-only; `.gitattributes` sets `merge=union`, so appends from parallel tasks never conflict |
| `**/pyproject.toml` dependency arrays, `apps/console/package.json` dependency maps | on conflict keep the union of both sides' entries (one entry per package; when both sides constrain the same package differently keep the narrower constraint that still admits the `versions.yaml` version), then regenerate the lockfile. Any other edit to these files must be in the task's `owns` |
| Empty `__init__.py` package markers (size 0, or a single docstring line) | identical additions merge cleanly; `check_ownership.py` rejects non-empty ones outside `owns` |
| `uv.lock`, `apps/console/package-lock.json` | never hand-merged: on conflict take `origin/develop`'s version, then run `uv lock` / `npm --prefix apps/console install --package-lock-only` and commit `chore: regenerate lockfile` |
| Generated files: `deploy/root/files/versions.yaml`, `deploy/charts/platform-config/files/versions.yaml` (PG-27), `.github/versions.env`, `infra/terraform/*/versions.auto.tf`, `services/api/openapi.json`, `apps/console/lib/api-types.ts`, `prompts/HASHES.json` | never hand-merged: on conflict take either side, then regenerate with `uv run python scripts/render_versions.py`, `task api:openapi`, `npm --prefix apps/console run gen:api`, `uv run python -m rootline_agent.prompts --write-hashes`; commit `chore: regenerate generated files` |
| `tests/registry/<TST-ID>--<task-id>.yaml` (one file per named test per task) | new files only; a task never edits another task's registry file |
| `tests/smoke/<component>.yaml` (one file per component) | new files only, owned by the deploying task |

`wiki/status.md` is written only by the coordinator. `scripts/check_ownership.py --task <id> --base <stage base sha> --branch <task branch>` fails (exit 1) when a task branch changes anything else; on the integration branch, G1 uses `--stage <id>` instead (§7.7). Renames count as a deletion of the old path plus an addition of the new path, and both paths are checked (`git diff --no-renames`, PG-21).

### 7.5 Dispatch and per-task review loop

For each task in a stage:
1. Coordinator completes the task's `pre_steps`.
2. Coordinator dispatches `rootline-implementer` (`model: "sonnet"`, `effort: "high"`, `isolation: "worktree"` when parallel) with `task_id`, `plan_file`, `branch`, `base` (parallel: the stage base = `origin/develop` tip when the stage starts, recorded in `.swarm/stages/<stage>.json`; sequential: the current `origin/develop` tip), `stage`, `mode: implement`.
3. On `STATUS: DONE`, coordinator dispatches `rootline-reviewer` (`model: "opus"`, `effort: "high"`) with `kind: task`.
4. `CHANGES_REQUIRED` → implementer again with `mode: fix-review` and the findings; then review again. After **3** failed rounds the coordinator dispatches `rootline-planner` to re-plan the task; a re-plan that changes scope, cost or security goes to the owner.
5. `STATUS: BLOCKED` → planner decides (contract change, ownership change, task split); the coordinator updates the schedule only through the planner.

### 7.6 Integration of a parallel stage

When every task of the stage has `APPROVE`:

1. `git fetch origin && git switch -c integration/<stage id lowercase> <stage base>` and push it.
2. For each task **in schedule order**, the task PR targets this branch; the coordinator merges it with a merge commit (`gh pr merge <n> --merge --body "Co-Authored-By: Claude Haiku 5.5 <noreply@anthropic.com>"`, §7.1 "Commit attribution trailers"). On a conflict:
   - only always-allowed paths (§7.4) → apply the §7.4 handling, commit, continue;
   - any other path → dispatch the implementer of the **later** task with `mode: resolve-conflict` to rebase its branch onto the integration branch tip and force-push its task branch (task branches are unprotected); then the reviewer re-reviews only the resolution diff; then retry the merge. If the reviewer finds the conflict is a design clash, the planner designs the resolution.
3. Run the integration gate (§7.7) on the integration branch.
4. Dispatch `rootline-reviewer` with `kind: integration`.
5. Open the integration PR `integration/<stage> → develop`, titled `feat(w<N>): integrate <stage> (<task IDs>)`, whose body lists every task PR, the gate report summary and the reviewer verdict, plus the WIK-020 wiki pages changed. The coordinator updates `wiki/status.md` in this PR. CI (`ci / required`) must pass; then squash-merge (GEN-021) with the squash block of §7.1 "Commit attribution trailers".
6. Run the stage's deferred steps in their `deferred_to` stage on the new `develop`.
7. Delete the integration branch and the task branches.

Sequential tasks skip steps 1–2 and 5: they open their PR straight into `develop`, run the gate on their own branch (`--branch feat/...`), get a task review, and are squash-merged with the squash block of §7.1 "Commit attribution trailers".

### 7.7 Integration gate (`scripts/integration_gate.py`, created by W1-T16)

`uv run python scripts/integration_gate.py --stage <id> [--branch <name>] [--base origin/develop] [--report-only]` runs these checks in order and writes `.swarm/gates/<stage>.json` (`{stage, branch, base_sha, head_sha, started_at, checks: [{name, status: pass|fail|skip, reason, duration_s, output_tail}]}`; `.swarm/` is gitignored). A check whose tooling or inputs do not exist yet is `skip` with the reason; every other check must `pass`. Any `fail` → the gate exits 1 (exit 0 with `--report-only`).

Setup and exit codes (PG-21, ADR 0040 item 8; full table in W1-T16 "Interfaces"):

| Situation | Report | Exit |
|---|---|---|
| unknown stage, or a `--base`/`--branch` ref that `git rev-parse --verify <ref>^{commit}` cannot resolve | none written, no worktree created; stderr `unknown stage: <id>`, `cannot resolve base <ref>` or `cannot resolve branch <ref>` | 2 (also with `--report-only`) |
| `git worktree add --detach` of `.swarm/worktrees/<stage>` or `.swarm/worktrees/<stage>-base` exits non-zero | `checks` = exactly one entry `{name: "setup worktree", status: "fail", reason: "git worktree add <path> failed: <git stderr>", duration_s: 0.0, output_tail: ""}`; any worktree already created is removed | 1 (0 with `--report-only`) |
| `uv sync --all-packages --frozen` in the branch worktree exits non-zero | `checks` = exactly one entry `{name: "setup uv-sync", status: "fail", reason: "exit <code>", duration_s: 0.0, output_tail: <last 40 lines>}`; both worktrees are removed | 1 (0 with `--report-only`) |
| setup succeeds | one entry per G-check (G1 to G11, names in W1-T16 "Interfaces"); both worktrees are removed | 1 on any `fail`, else 0 (0 with `--report-only`) |

| # | Check | Passes when | Applies when |

### 7.8 Failure handling

| Failure | Action |
|---|---|
| Gate check fails on an integration branch | the coordinator maps the failure to a task by the failing path or test file owner (schedule `owns`); dispatches that implementer with `mode: fix-gate` on its task branch; re-merges; re-runs the gate. After 3 rounds: planner |
| Failure cannot be attributed to one task | planner designs the fix; an implementer applies it on a branch `fix/<stage>-integration` merged into the integration branch |
| `develop` CI red after an integration PR merged | the coordinator reverts the squash commit with a PR `revert: <title>` immediately, then treats it as a gate failure |
| Deferred cluster step fails (G12) | gate-failure handling on a `fix/<slug>` branch into `develop`; the stage is not complete until G12 passes |
| Subagent model unavailable | stop and ask the owner (CLAUDE.md) |

### 7.9 Coordinator loop (per week)

1. `uv run python scripts/swarm_schedule.py next --week <N>` prints the next runnable stage (all `after` stages complete per `.swarm/progress.json`). Exact output and exit codes (PG-21, ADR 0040 item 3):

   | Situation | Printed line (exact) | Exit | Coordinator action |
   |---|---|---|---|
   | a stage is runnable | the stage ID, for example `W1-P2` (the first not-done stage of week N in schedule order whose `after` stages are all done) | 0 | run that stage (step 2) |
   | every stage of week N is done | `week N complete` (for example `week 1 complete`) | 0 | finish the week (wave acceptance, MS-001), then start week N+1 |
   | stages remain, none runnable | `no runnable stage in week N; not done: <ids>` (`<ids>` = the not-done stage IDs of week N in schedule order, joined by `, `) | 1 | stop and dispatch the planner with the printed line (a stage's `after` names a stage that is not done) |
   | week N not in the schedule | `unknown week: N` | 1 | stop and report to the owner |
2. Run the stage per §7.5–§7.6 (parallel) or §7.5 + direct PRs (sequential).
3. Record completion: `uv run python scripts/swarm_schedule.py done <stage>`; update `wiki/status.md`.
4. Repeat until the week's last stage; then run the wave's **Acceptance** section and the release PR (MS-002), which also runs `e2e.yml` from week 6 on.
