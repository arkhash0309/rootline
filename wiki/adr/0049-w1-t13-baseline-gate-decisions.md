# 0049 — Telemetry names, alert rule layout and baseline gate decisions from W1-T13 (spec-gap)

Status: accepted
Date: 2026-11-28
Label: spec-gap
Plan gap: PG-30 (`docs/superpowers/plans/2026-11-26-rootline-00-overview.md` §5)

This ADR holds eight decisions, D1 to D8, taken by the implementer of plan task W1-T13 (`docs/superpowers/plans/2026-11-26-rootline-w1-foundations.md` "Task W1-T13", branch `feat/w1-baseline-gate`) while it expressed spec §6.5 in the names of the running stack (WKL-022) and built the alert rules and the baseline gate (WKL-004, WKL-030, WKL-031, WKL-032). None of them changes cost, security level or scope; each follows spec §0.3 (simplest, cheapest, safest). The facts they rest on are recorded in `wiki/components/telemetry.md` (findings F1 to F10). A ninth decision, D9 (`HighCPU` against an absolute threshold of `1.5` cores), was taken by the planner on 2026-11-28 for the defect that the W1-T13 review left open; the planner also confirmed D1 to D8 (section "Planner confirmation").

## Decision

**D1 — Names (WKL-022).** `metric-map.yaml` uses these expressions (the full templates are in `deploy/charts/observability/files/metric-map.yaml`):

| Key | Metric and label names |
|---|---|
| `request_rate`, `error_ratio`, `latency_p50`, `latency_p95`, `latency_p99` | `traces_spanmetrics_calls_total` and `traces_spanmetrics_latency_bucket` with `service`, `span_kind="SPAN_KIND_SERVER"`, `status_code="STATUS_CODE_ERROR"` (as spec §6.5) |
| `cpu_usage`, `memory_working_set`, `restarts` | `container_cpu_usage_seconds_total`, `container_memory_working_set_bytes`, `kube_pod_container_status_restarts_total` with `namespace="shop"` and the pod regex of D2 |
| `kafka_consumer_lag` | `sum(kafka_consumer_records_lag{service_name="$svc",k8s_namespace_name="shop"})`, `services: [fraud-detection]`, `jvm_only: false` |
| `gc_pause` | `sum(rate(jvm_gc_duration_seconds_sum{service_name="$svc",k8s_namespace_name="shop"}[5m]))`, `services: [ad, fraud-detection]`, `jvm_only: true` |

`$svc` equals `$wl` for all 19 kept components (telemetry.md F5), so the spec sentence "equal for every kept component unless week 1 discovers otherwise" resolves to "equal".

**D2 — Pod regex.** `$wl-[a-z0-9]+-[a-z0-9]+` replaces `$wl-.*` in `cpu_usage`, `memory_working_set` and `restarts`. The same regex is used by `scripts/baseline_gate.py` (`pod_regex`) and by the `limit` series of `HighMemory` (`HighCPU` has no limit series after D9).

**D3 — `error_ratio`.** Numerator and denominator are each wrapped as `(sum(...) or vector(0))`; the denominator keeps `clamp_min(..., 1e-9)`. Result: `0.0` for a service without errors or without server spans.

**D4 — `gc_pause` window.** `[5m]` instead of `[1m]` (the minimum that always holds two 60 s samples, with margin for one lost export).

**D5 — Percentile.** `scripts/derive_thresholds.py` implements the percentile in pure Python with linear interpolation (`low + (high - low) * fraction` on the rank `(n - 1) * q / 100`), which equals the default method of `numpy.percentile`. No dependency is added, so `versions.yaml` and `uv.lock` do not change. Test `tests/repo/test_thresholds.py::test_baseline_p95_uses_95th_percentile` asserts `95.05` for the values `1.0` to `100.0`, the value the plan names. Non-finite samples (NaN, `Inf`) are dropped before the percentile; a service without a finite sample gets `baseline_p95 = 0.0`, `ServiceHighLatency = 1.0`, and the lag service gets `KafkaConsumerLagHigh = 1000.0`.

**D6 — Rule layout.** The PrometheusRule `rootline-workload` has one group and 89 rules:

| Alert | Rules | Selector | `service` label |
|---|---|---|---|
| `ServiceHighErrorRate`, `ServiceHighLatency` | 13 each | `rootlineAlerts.serverServices` of `values.yaml` (13 kept server-side services of D7) | static `service: <svc>` |
| `PodCrashLooping`, `HighCPU`, `HighMemory` | 19 each | `rootlineAlerts.workloads` (all 19 kept components, WKL-002) | static |
| `KafkaConsumerLagHigh` | 1 | `rootlineAlerts.kafkaLagService` (`fraud-detection`) | static |
| `PodNotReady`, `DeploymentReplicasUnavailable`, `ContainerWaiting`, `PodUnschedulable`, `ContainerOOMKilled` | 1 each | whole namespace `shop` | none; the expression ends in `label_replace(..., "service", "$1", "pod", "(.*)-[a-z0-9]+-[a-z0-9]+")` (`"deployment", "(.*)"` for `DeploymentReplicasUnavailable`) |

The plan also names the StatefulSet regex `(.*)-[0-9]+`; it is not rendered because the workload render has no StatefulSet (`wiki/components/workload.md` finding (b)), and a second `label_replace` could rewrite a Deployment pod whose hash ends in digits only. `HighMemory` divides `memory_working_set` by `sum(kube_pod_container_resource_limits{namespace="shop",resource="memory",pod=~<D2>})`; a workload without a limit series yields an empty vector, which is the "excluded by the limit series" rule of the plan (all 19 containers have a memory limit, telemetry.md F9). `HighCPU` compares `cpu_usage` with the absolute threshold of D9 and has no limit series. (Superseded text, kept for the record: the first W1-T13 render divided `cpu_usage` by the `resource="cpu"` limit series; that rule could never fire, because the render has no CPU limit.) `fraud-detection` has no `SPAN_KIND_SERVER` series (telemetry.md F4), yet it is one of the 13 `rootlineAlerts.serverServices` (D7), so its `ServiceHighErrorRate` and `ServiceHighLatency` rules are rendered. Both can never fire: the `error_ratio` expression is `0.0` by D3 and the `latency_p95` expression returns no series, because the service produces no server spans. The rules are kept so that the list stays equal to the 13 gate services; `fraud-detection` is effectively covered by `PodCrashLooping`, `HighMemory` and `KafkaConsumerLagHigh`. Numbers in thresholds are written with Go `%v` (`1`, `1.5`, `1000`); `for` values and severities equal the WKL-031 table (`tests/repo/test_alert_rules.py::test_every_alert_follows_the_wkl_031_table`).

**D7 — Baseline gate.** `scripts/baseline_gate.py` treats these 13 components as the kept server-side services: `frontend`, `ad`, `cart`, `checkout`, `currency`, `email`, `payment`, `product-catalog`, `quote`, `recommendation`, `shipping`, `fraud-detection`, `image-provider` (`KEPT_COMPONENTS` minus `load-generator`, `frontend-proxy`, `kafka`, `valkey-cart`, `astronomy-db`, `flagd`). Before it starts it checks with `kubectl` that every flag in `ConfigMap/shop/flagd-config` has `defaultVariant: "off"` and that `Deployment/shop/load-generator` has `LOCUST_USERS=10` (WKL-004 "all flags off and load `normal`"); otherwise it exits `2`. `error_ratio` is `avg_over_time((<metric-map error_ratio>)[30m:15s])` at the end time; `restarts` is `sum(increase(kube_pod_container_status_restarts_total{namespace="shop",pod=~<D2>}[30m]))`. A value that does not exist is `FAIL` ("no data"). Because D3 wraps both sides of `error_ratio` in `or vector(0)`, `error_ratio` can never be "no data": the no-data-is-FAIL rule applies only to `restarts`, and a service without any traffic or without server spans gets `error_ratio = 0.0` and passes the gate on that column. `fraud-detection` has no server spans, so its `error_ratio` is `0.0` by D3 and it is judged on restarts. `scripts/baseline_gate.py` exits `2` (not `1`) whenever the cluster state cannot be read: `kubectl` missing or not executable, a `kubectl` timeout of 600 s, a non-zero `kubectl` exit status, output that is not JSON, a ConfigMap without `data`, a container without `env`, or a failure to start the port-forward. Exit `1` means that at least one row is `FAIL`. `samples.json` and `report.json` go to `data/baseline/<date>/` (directory `data/` is git-ignored); only `deploy/values/alert-thresholds.yaml` and its chart copy are committed.

**D8 — Alertmanager.** `templates/alertmanager-config.yaml` of chart `observability` renders ExternalSecret `observability/alertmanager-webhook` (`refreshInterval: "0"`, `dataFrom` `generatorRef` Password `password-48`, target Secret `alertmanager-webhook` with `type: Opaque` and the single key `token` = `{{ .password }}`) and `AlertmanagerConfig` `observability/rootline` exactly as WKL-032 (route, one receiver `rootline-api`, which the operator names `observability/rootline/rootline-api`, `sendResolved: true`, `httpConfig.authorization` `type: Bearer` with `credentials` from Secret `alertmanager-webhook` key `token`). `values.yaml` sets `kube-prometheus-stack.alertmanager.alertmanagerSpec.alertmanagerConfigMatcherStrategy: {type: None}`. The live generated Alertmanager configuration (verified 2026-11-28 in Secret `alertmanager-observability-kube-prometh-alertmanager-generated`, key `alertmanager.yaml.gz`) differs from the WKL-032 text "No other receivers" in these facts: (1) it has a second receiver `null` (the kube-prometheus-stack default, with no `webhook_configs`), used by the root route (`receiver: "null"`, `group_by: [namespace]`) and by the route for `alertname = "Watchdog"`; (2) the chart default `inhibit_rules` are present (four rules; they compare `severity` and `alertname`, or `InfoInhibitor`) and have no effect on Rootline alerts, because each `alertname` carries a single severity (WKL-031 table) and `equal` includes `alertname`, and Rootline defines no `info` alert; (3) the operator sets `continue: true` on the `rootline` route, which has `group_by: [alertname, service]`, `group_wait: 30s`, `group_interval: 2m`, `repeat_interval: 1h` and, with `alertmanagerConfigMatcherStrategy.type: None`, no `namespace` matcher; (4) the receiver is named `observability/rootline/rootline-api`, not `rootline-api`. Reading adopted: WKL-032 means "no other notifying receiver"; the `null` receiver discards, so every alert that matches the `rootline` route reaches `api` and nothing else notifies. This round does not change the Alertmanager configuration. The `rootline` namespace ExternalSecret and the ClusterSecretStore `observability-reader` are not created in W1-T13: they are W4-T13 (plan Step 7 states the order). The NetworkPolicy `allow-egress-pods` of chart `observability` already allows Alertmanager egress to namespace `rootline`.

**D9 — `HighCPU` against an absolute threshold (planner, 2026-11-28; option (b)).** WKL-031 row `HighCPU` becomes `cpu_usage > 1.5` (cores), `for: 2m`, severity `warning`, one rule per workload of `rootlineAlerts.workloads` (19 rules, unchanged count; the PrometheusRule keeps 89 rules). The spec text of WKL-031 is edited accordingly (spec §6.5). No CPU request or CPU limit is added to any workload, `scripts/render_workload.py` and WKL-010 do not change, no `baseline-v3` is rendered and the baseline gate is not run again, because the rule change does not touch the workload. The value is a literal in the template (like `0.9` of `HighMemory`), not a † threshold, and `deploy/values/alert-thresholds.yaml` does not change.

| Item | Value |
|---|---|
| Expression of the rule for workload `<svc>` | `(<cpu_usage of metric-map.yaml with $wl = <svc>>) > 1.5`, for `frontend`: `(sum(rate(container_cpu_usage_seconds_total{namespace="shop",pod=~"frontend-[a-z0-9]+-[a-z0-9]+",container!="",container!="POD"}[1m]))) > 1.5` |
| `for` / severity / labels | `2m` / `warning` / `rootline: "true"`, `namespace: shop`, `service: <svc>`, `severity: warning` (unchanged) |
| Annotation `summary` | `Workload <svc>: CPU usage above 1.5 cores for 2 minutes` |
| Template change | `deploy/charts/observability/templates/prometheusrule-workload.yaml`: delete the `$cpuLimit` line; `expr: {{ printf "(%s) > 1.5" $cpu \| quote }}`; `summary: {{ printf "Workload %s: CPU usage above 1.5 cores for 2 minutes" $svc \| quote }}` |
| Test change | `tests/repo/test_alert_rules.py`: the `HighCPU` assertion becomes: for each of the 19 rules, `expr` equals `"(" + <cpu_usage promql with $wl and $svc replaced by the rule's service> + ") > 1.5"`, and `"kube_pod_container_resource_limits"` does not occur in `expr`; the rule count (89) and the `("2m", "warning")` table entry stay |

Why `1.5` cores, `2m`:

| Case | `cpu_usage` (cores) | Result with `> 1.5` for `2m` |
|---|---|---|
| Every workload at load `normal`, measured (D9 context row) | highest 2 min value `0.5967` (`load-generator`); highest 1 m value `0.8052`; all other workloads at most `0.1176` | does not fire (margin `0.9033` cores on the 2 min value) |
| `load-generator` at load `high` (`LOCUST_USERS=20`, WKL-040), estimate `2 × 0.5967` | `1.1934` (unverified 2026-11-28; measured in the W1-T13 fix round, see below) | does not fire (estimated margin `0.3066` cores) |
| C06 `chaos-cpu-stress`: `StressChaos` cpu `workers: 2`, `load: 100` on `currency`, `product-catalog` or `recommendation`, no CPU limit, node has 16 CPUs (`nproc` = `16`) | `2.0` plus the target's own load (`0.0043`, `0.1176`, `0.0323`); the stressors run in the target container's cgroup (unverified 2026-11-28; checked by the W2-T13 run of C06) | fires: `rate(...[1m])` passes `1.5` about 45 s to 60 s after `ti` (15 s scrape interval), the rule fires 2 min later and at most one 30 s evaluation interval (`evaluation_interval: 30s`, verified 2026-11-28) after that, between `ti + 3 min` and `ti + 3 min 30 s`: inside the 4 min stress and the 6 min wait of LAB-041 step 3 |
| F07 `flag-ad-high-cpu` (`adHighCpu` = `on`) | the upstream `ad` service starts 4 busy-loop threads (`CPULoad`, app `3.1.0`; unverified 2026-11-28; checked by the W2-T13 run of F07), about `4.0` | fires between 3 min and 3 min 30 s after the flag is effective (LAB-020 `effective_at`: observed within 120 s of `injected_at`, else `injected_at + 90 s`), so at the latest at `ti + 5 min 30 s`, inside the 6 min wait of LAB-041 step 3 |
| JVM start of `ad`, `fraud-detection` or `kafka` after a restart | short bursts | `for: 2m` filters bursts shorter than 2 min |

C06 and F07 work under D9. They also work without any CPU alert: LAB-041 step 3 accepts the first firing `rootline: "true"` alert of any name, falls back to `trigger_kind = synthetic_report` after 6 min, and LAB-044 judges "no effect" by alerts and by anomalies with `|z| >= 3.5`. D9 restores the CPU alert that the resource-exhaustion rows C06 and F07 are expected to raise on their target.

Verification obligations (decision rule and default):

1. **W1-T13 fix round** (implementer, branch `feat/w1-baseline-gate`), after syncing the changed rule: (i) Prometheus `/api/v1/rules` lists group `rootline-workload` with 89 rules, all `health: ok`, every `HighCPU` rule `state: inactive`; (ii) high-load check: `kubectl --context k3d-rootline -n shop set env deployment/load-generator LOCUST_USERS=20`, wait 10 min, query `max_over_time(min_over_time((sum(rate(container_cpu_usage_seconds_total{namespace="shop",pod=~"load-generator-[a-z0-9]+-[a-z0-9]+",container!="",container!="POD"}[1m])))[2m:15s])[8m:15s])`, record the value in `wiki/components/telemetry.md` F9, then `kubectl --context k3d-rootline -n shop set env deployment/load-generator LOCUST_USERS=10` and wait until `kubectl --context k3d-rootline -n shop rollout status deployment/load-generator --timeout=300s` exits `0`. Rule: a value below `1.5` keeps D9 unchanged (default). A value of `1.5` or more stops the fix round; the coordinator dispatches the planner, who re-decides the `load-generator` rule before the W2 capture. A `kubectl` failure or a query without a result is reported as a fix-round failure (overview §7.5), and `LOCUST_USERS` is reset to `10` before the round ends in every case.
2. **W2-T13 Step 3** (first capture batch): `wiki/eval/dataset.md` records for the base scenarios of C06 and F07 whether `trigger_alerts` contains `alertname = HighCPU` with `service` = the target. Rule: when it does, nothing changes (default). When it does not, the captured snapshot stays valid (LAB-041 and LAB-044 decide its status, not D9), and the coordinator dispatches the planner to re-decide the threshold before the next capture batch.

## Consequences

- `deploy/charts/observability/files/metric-map.yaml` is the single PromQL source named in the W1-T13 interfaces; W2-T09 and W3-T06 read it unchanged.
- Spec §26 gets one row (PG-30). The WKL-030 table of spec §6.5 is not edited: it keeps the template as written, `metric-map.yaml` holds the finalised form, as WKL-022 and WKL-030 say ("label names finalised per WKL-022"). The WKL-031 row `HighCPU` is edited by D9 (`cpu_usage > 1.5`, cores, PG-30); no other WKL-031 row changes.
- **`HighCPU` defect, decided by D9 (option (b), planner, 2026-11-28).** The review of W1-T13 found that none of the 19 containers of namespace `shop` has a CPU request or a CPU limit (verified 2026-11-28, `kubectl --context k3d-rootline -n shop get pods -o json`: 19 containers, 0 with `resources.requests.cpu` or `resources.limits.cpu`), so the first rendering of the 19 `HighCPU` rules (`cpu_usage / cpu limit > 0.9`) could never fire. D9 redefines the rule as `cpu_usage > 1.5` for `2m`. Literal consequences: (1) a W1-T13 fix round changes `deploy/charts/observability/templates/prometheusrule-workload.yaml` and `tests/repo/test_alert_rules.py` exactly as the D9 table says, and performs D9 verification obligation 1; (2) no workload render change, no `baseline-v3`, no new gate run, `deploy/values/alert-thresholds.yaml` unchanged; (3) W2-T13 Step 3 performs D9 verification obligation 2; (4) the memory budget (ARC-030), the Alertmanager configuration (D8) and the Tempo limit are not changed; (5) ADR 0046 T7 (no CPU request or limit in W1 values) stays valid.
- Not decided here, handed to the W2-T05 catalogue task: G08 `git-unschedulable-request` names the acceptable action "`set_resources` with cpu_request ≤ baseline limit", but no baseline container has a CPU limit (D9 keeps it that way), and POL-020 bounds `set_resources` to `cpu 50m–2000m` and "each new value between 0.25× and 4× the current value", which from the injected `64` cores allows no value below `16` cores. That acceptable action can therefore never be proposed within bounds; `revert_commit(<sha>)` is unaffected.
- Telemetry finding F10 (Tempo OOMKilled 23 times in 11 h 49 min at its `768Mi` limit, measured 2026-11-28 17:14 UTC) is reported to the coordinator and the owner; this task does not change memory limits, because ARC-030 owns the memory budget.
- The gate result and the thresholds it produced are recorded in `wiki/components/workload.md` section "Baseline health gate".

## Alternatives considered

| Option | Why not |
|---|---|
| Keep `$wl-.*` and accept the `frontend` over-count (D2) | wrong `cpu_usage` for `frontend`, and a false `restarts` hit when `frontend-proxy` restarts |
| Add `numpy` to the workspace (D5) | a new dependency, a `uv.lock` change and a version pin for a ten-line function |
| One cluster-wide rule per alert for `PodCrashLooping`, `HighCPU`, `HighMemory` (D6) | the plan and WKL-031 say per service; per-workload rules reuse the `metric-map.yaml` templates unchanged |
| Create the `rootline` copy of the webhook token now (D8) | the namespace `rootline` has no consumer until W4-T13; the plan assigns it there |
| Scale `latency_p95` thresholds from the gate's own PASS window only | that is what the plan prescribes: thresholds derive from the same 30 minute baseline run |
| D9 option (a): WKL-010 adds CPU limits to the workload render, re-render `baseline-v3`, re-run the gate | not simplest: needs 19 per-container CPU values that no document fixes, a render change, a `rootline-env` PR and tag, and a new 30 min gate run; not safest: CPU limits throttle the JVM services `ad`, `fraud-detection` and `kafka` and can change the baseline that already passed; it also contradicts ADR 0046 T7 (no CPU request or limit in W1) |
| D9 option (c): drop `HighCPU` | removes the only CPU alert, so C06 and F07 (category `resource_exhaustion`) could raise only latency or error alerts or fall back to `synthetic_report`; it narrows the alert catalogue the spec defines |
| D9 threshold `1.0` core | `load-generator` at load `high` is estimated at `1.1934` cores held for 2 min and would fire during every `high` load scenario, which also fails LAB-041 step 1 ("no firing `rootline: "true"` alerts for ≥ 5 min") |
| D9 threshold `1.9` cores | C06 adds `2.0` cores; a threshold this close leaves `0.1` core margin against stressor scheduling on a busy node |

## Planner confirmation (2026-11-28)

The planner (overview §7, spec-gap decisions) reviewed D1 to D8 against the spec, the branch `feat/w1-baseline-gate` at `83074d3` and the live cluster `k3d-rootline`.

| Decision | Verdict | Basis |
|---|---|---|
| D1 | CONFIRMED | names match telemetry.md F5 and F8; WKL-030 allows finalised label names |
| D2 | CONFIRMED | `[a-z0-9]+` cannot contain `-` and PromQL regex matchers are fully anchored, so `<wl>-[a-z0-9]+-[a-z0-9]+` matches only pods of Deployment `<wl>` and never a pod of a workload whose name is `<wl>-<word>` (`frontend-proxy`) or ends in `-<wl>` (`valkey-cart`); all 19 workloads are Deployments (workload.md finding (b)) |
| D3 | CONFIRMED | `sum(...) or vector(0)` adds the label-less `0` only when the `sum` is empty, so no series is duplicated; `ServiceHighErrorRate` (`error_ratio > 0.05 and request_rate > 0.1`) still needs traffic to fire |
| D4 | CONFIRMED | `[5m]` holds at least four 60 s samples (telemetry.md F8) |
| D5 | CONFIRMED | rank `(n - 1) × q / 100` with linear interpolation equals the `numpy.percentile` default; for `1.0` to `100.0` and `q = 95` the rank is `94.05`, giving `95.05` |
| D6 | CONFIRMED with the `HighCPU` change of D9 (applied in this ADR's D6 text); rule count stays 89 | the five kube-state-metrics rules omit a static `service` label, so the `label_replace` result is kept; `defaultRules.create: false` (`deploy/charts/observability/values.yaml`) means no chart rule competes |
| D7 | CONFIRMED | the lenient `error_ratio` of D3 did not hide a service without traffic in this run: over the 2 h before 2026-11-28 17:18 UTC every server-side service except `fraud-detection` had `sum(rate(traces_spanmetrics_calls_total{span_kind="SPAN_KIND_SERVER"}[2h]))` of at least `0.1061` req/s (`payment`), and `fraud-detection` has no server spans by design (telemetry.md F4) |
| D8 | CONFIRMED | `defaultRules.create: false` leaves no chart alert (not even `Watchdog`) that the matcher-less `rootline` route could forward; `api` ignores any alert without `rootline="true"` and `namespace="shop"` (API-040 step 1); the discarding receiver `null` does not notify |
